## Decisions Made
- Kept `stockColorClass` and `StockQuantityInput` in the same file, matching the plan's export contract (`exports: ["StockQuantityInput", "stockColorClass"]` from a single module) rather than splitting the helper into its own file.
- Inlined the `h-11 w-11` button className literally on both the `−` and `+` buttons instead of factoring it into a shared constant, matching `QuantityStepper.tsx`'s existing convention of per-button literal classNames.
- In `DeactivateDialog.test.tsx`, used `getByRole(..., { hidden: true })` for the button queries rather than changing component behavior — the mocked `showModal`/`close` don't toggle the native `open` attribute the way a real browser does, so jsdom's `dialog:not([open]) { display: none }` UA rule hides the buttons from the default accessibility-tree query. This is a test-only accommodation; it does not affect real-browser behavior, where `showModal()` sets `open` itself.

## Deviations from Plan

None - plan executed exactly as written. The `hidden: true` test-query adjustment above is a test-authoring detail within Task 3's scope, not a deviation from any locked decision, interface, or acceptance criterion.

## Issues Encountered

- First test run of `DeactivateDialog.test.tsx` failed 3 assertions with `TestingLibraryElementError: Unable to find an accessible element with the role "button"`. Root cause: the `beforeEach` shim assigns `vi.fn()` to `showModal`/`close`, but a mock function doesn't perform the real browser side effect of toggling the `<dialog>` element's `open` attribute — so jsdom's default `dialog:not([open]) { display: none }` stylesheet rule left the dialog's contents outside the default (visible-only) accessibility tree that `getByRole` queries against. Fixed by adding RTL's `hidden: true` option to the three affected `getByRole('button', ...)` queries, with an inline comment explaining why. No component code changed.
- `HTMLDialogElement.prototype.showModal = vi.fn()` initially failed `tsc --noEmit` (`Mock<Procedure | Constructable>` not assignable to `() => void`). Fixed with an explicit `as unknown as () => void` / `as unknown as (returnValue?: string) => void` cast on the two assignments.
