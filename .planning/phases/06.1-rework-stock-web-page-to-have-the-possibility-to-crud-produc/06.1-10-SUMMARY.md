# Phase 06.1 Plan 10: Wire create/add-variant panels and D-18 recovery Summary

**Mounted `CreateProductPanel` and `AddVariantPanel` into `Stock.tsx` behind their Active-view-only triggers, and implemented the D-18 partial-failure recovery that pre-seeds a failed add-variant's intended count and SKU-specific amber warning into the existing pending/Save-all state instead of a generic error banner.**

## Performance

- **Duration:** ~45 min
- **Completed:** 2026-08-07T09:34:14Z

## Accomplishments
- INV-05: a product created from `/stock` (name, base price, category, generated size/colour variants with opening stock) appears in the Active list immediately, no page reload
- INV-07: a variant added to an existing product goes through `putProductVariants` then `batchAdjustStock` in one action, closing the panel and refetching
- D-18: when the follow-up stock write fails after the variant PUT succeeds, the panel closes, the new variant renders as a normal editable row pre-marked dirty with its intended (not 0) count, carrying the exact locked warning copy, and recovery is a single existing "Save all" click
- Final assembly closed both absence guarantees for the whole phase: no content editor (D-10) and no variant-removal control (D-16) exist anywhere on the page

## Decisions Made
- Commits were split by task via a temporary remove-verify-commit-reapply sequence rather than one combined commit, because both Task 1 and Task 2 land in the same file with additive-only diffs that would otherwise be indistinguishable — this preserves per-task atomicity without losing any code.
- `onPartialFailure`'s `message` argument is deliberately not surfaced anywhere in the UI (only accepted and ignored, per the plan's explicit instruction and RESEARCH Pitfall 2) — the SKU-specific row warning is the only required signal for this failure path.
