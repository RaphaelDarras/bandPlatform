# Phase 06.1 Plan 09: Inline stock editing, Save-all batch commit, and label editing Summary

**Every variant row across the catalogue is now inline-editable (±1 buttons + absolute set-count field writing one pending value), committed by a single all-or-nothing `POST /api/inventory/restock/batch` click, with independent inline size/colour editing that never touches the batch's dirty count — INV-06 delivered in full.**

## Accomplishments
- Exported `rowKey(productId, sku)` and `pending`/`rowErrors` state; `StockQuantityInput` rendered exactly once, inside the Active-view branch only, bound to `pending[key] ?? v.stock` with no clamp/floor (D-07) and a client-side integer check per row (D-04 stays unwritten: no reason/preset/audit control anywhere)
- Dirty-row treatment (`border-l-[3px] border-l-[var(--color-accent)]` + `bg-[rgba(200,188,134,0.06)]`) applied per UI-SPEC §1, Active view only
- Sticky `bottom-0` Save-all footer with the four UI-SPEC §2 states (Idle/Dirty/Saving/Error) and a "Discard changes" companion link; renders only when `data` has loaded and `view === 'active'` (D-26)
- `handleSaveAll` builds `{ productId, variantSku, quantity: pendingStock - serverStock }` deltas entirely from in-memory state at click time — no `fetchStock`/`loadStock` call precedes `batchAdjustStock` (D-03, binding); zero-deltas filtered, >100 adjustments blocked client-side with the exact copy from the plan
- On failure: banner reads `Save failed — nothing was saved. {message} Your changes are still here.`, and `pending`/`rowErrors` are left completely untouched (D-06) — verified by a test that types `10` against a server value of `3`, fails the batch, and asserts the input still shows `10` and the footer still reads `Save all changes (1)`
- Inline Size/Color `<input>`s (Active view only) persist on blur via `putProductVariants(token, productId, fullArray)` where `fullArray` is every variant of that product with only the edited field replaced (D-17/D-20); `priceAdjustment` is never rendered editable anywhere on the page
- Label edits are deliberately decoupled from the stock batch: they never move `dirtyCount`, never disable/enable the Save-all button, and use their own row-scoped `"Couldn't save this change — try again."` error, never the batch banner
- `Stock.test.tsx` extended from 10 to 21 cases covering dirty-count growth, the `(was N)` caption + Discard changes, the D-03 delta-not-absolute payload with no re-fetch, a negative delta from `2 → -1`, the D-06 all-or-nothing failure banner, success clearing pending, D-30's mid-save `AuthExpiredError`, the D-04 negative assertion, the D-20 full-variant-array assertion plus the "no price adjustment control" assertion, label-save failure isolation, and D-26's Archived-view lockdown

## Decisions Made
- `rowWarnings` state was declared in Task 2's commit (not Task 1's) purely to satisfy `noUnusedLocals`: the setter has no call site until this plan clears it on save-success/discard, and plan 06.1-10 is the one that actually *sets* a warning message. Splitting it this way kept every intermediate commit individually `tsc`-clean.
- Chose a single `renderLabelCell` helper (called for both Size and Color) over two near-duplicate inline blocks so the row-scoped failure copy is defined once, matching the plan's own grep-count acceptance check (`grep -c "Couldn't save this change — try again." Stock.tsx` == 1).
- Label inputs are uncontrolled (`defaultValue`, `onBlur`) rather than controlled+state-mirrored, so an optimistic local update or a background `loadStock` refresh after a successful save can never overwrite what's currently in the DOM node — avoids a whole class of "my typed value disappeared" bugs without extra synchronization code.

## Issues Encountered

- Initial attempt included `rowWarnings` state in Task 1 alongside `pending`/`rowErrors`; `tsc --noEmit` failed with `TS6133: 'setRowWarnings' is declared but its value is never read` because array-destructured hook setters ARE flagged by `noUnusedLocals` in this project's `tsconfig.json` (unlike the common assumption that they're exempt). Resolved by deferring the state to Task 2, where `handleDiscard`/`handleSaveAll`'s success path both call `setRowWarnings({})`.
- The D-20 label-editing test initially failed because a successful `putProductVariants` with no pending stock edits triggers `loadStock(token)`, and the test's single queued `fetchStock` mock value had already been consumed by the initial page load — the second call resolved to `undefined`, nulling out `data` and hiding the whole table. Fixed by queueing a second `fetchStock.mockResolvedValueOnce` before firing the blur event.
- A literal `"clamp"` inside an explanatory D-07 code comment tripped the plan's own `grep -c "Math.max|Math.min|clamp"` acceptance check (expects `0`). Reworded the comment to avoid the substring without changing its meaning.
